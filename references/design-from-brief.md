# 从文字需求到界面（Design from Brief）

> 读时机：用户只给功能描述/文字需求，没有参考产品、没有设计稿时。这是 skill 的**设计推理主流程**。
> 原则：每一步都产出「决策 + 理由」，理由写进 SPEC；没有理由的样式选择一律视为拍脑袋。

## 第 1 步：识别功能族（决定页面骨架的大类）

| 功能族 | 特征 | 骨架候选 |
| --- | --- | --- |
| 记录维护型 | 大量同类记录，增删改查为主 | 台账（标准/主从/卡片/高密度） |
| 单据处理型 | 有状态流转（草稿→提交→审核→完成） | 台账 + 详情页 + 操作条（审批/流转） |
| 流程跟踪型 | 多人多环节、有时限、有责任人 | 看板（按状态分列）+ 台账双视图 |
| 分析决策型 | 聚合指标、趋势、对比 | 概览页（KPI + 图表）+ 下钻台账 |
| 配置管理型 | 结构化参数、层级字典 | 树/双栏（左结构右内容） |
| 工具操作型 | 单一任务、高交互 | 单页工具（左输入右结果） |

> 一段需求里常混多个族：**拆开，各给一个页面**，不要塞进一屏。

## 第 2 步：定信息架构（导航怎么长）

1. 模块数 ≤5 且无层级 → 顶部导航；
2. 模块数 6–15 → 侧栏分组（每组 3–6 项，组名是用户的语言不是系统语言）；
3. 模块数 >15 或有多级业务域 → 侧栏两级 + 模块搜索；
4. 同一实体的不同视图（列表/详情/统计）→ 不加导航项，用页内切换。

## 第 3 步：选骨架（每个页面一个主骨架，不混用）

- 主骨架只选一个：台账 / 看板 / 概览 / 树-内容 / 工具 / 向导。
- 主骨架 + 最多 2 个辅助区（KPI 条、范围提示、批量条）。
- 若需要第三种交互（如审批流），用**抽屉或独立页**承载，不塞进主骨架。

## 第 4 步：定容器与字段（从数据形状推）

| 数据形状 | 容器 | 理由 |
| --- | --- | --- |
| 字段 ≤8 且从列表进入 | 抽屉 | 保留列表上下文 |
| 字段 9–20 / 需分组 | 独立页 | 需要纵向空间与锚点导航 |
| 需要多步决策 | 分步 | 降低单屏认知负荷 |
| 单值修改 | 弹窗 | 最小上下文切换 |

字段顺序：**识别字段（谁）→ 关键属性（是什么）→ 业务字段（怎么办）→ 备注/附件**。
必填项控制在 ≤40%：超过说明这个表单该拆。

## 第 5 步：定密度与视觉语气（用旋钮）

读 `references/design-knobs.md`，把需求里的语气词（"严肃""高效""轻快""给领导看"）翻成五旋钮取值。
没有语气词时按功能族默认：记录型=中密度高对比；分析型=低密度强层级；工具型=高密度中对比。

## 第 6 步：自检三问（不通过就改，别交付）

1. **删掉一半**：如果去掉 KPI、去掉说明文字，页面还成立吗？成立的才保留。
2. **三秒测试**：新人三秒内能否说出"这页是干什么的、下一步点哪"？
3. **名字测试**：把业务名词换成别的行业，页面还像样吗？像样说明没被业务绑死，是通用骨架——这是好事；但若**信息结构**也通用到看不出业务，说明设计太泛，需要用业务语言重写标签。

## 交付时必写（在 SPEC 或交付说明里）

- 功能族判断 + 骨架选择 + 容器选择 + 旋钮取值，各一句理由；
- **本版已知弱点 3 条**（自评，不需美化）；
- 若需求里有无法决定的信息（角色权限、数据量级），列为待确认，不要静默假设。
